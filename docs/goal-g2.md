## 一句话目标

**云乐坊内部的多个游戏项目（合计不超过 30 人）长期用 YunBox 存放开发素材：多人可以安全地同时编辑二进制素材，新成员自助接入，出问题能发现、能恢复，并且不依赖任何一个人手工维护。**

不面向外部用户，不做 SaaS 和计费。

## 「生产可用」的完成标准

全部满足才算完成：

1. **真实使用**：至少 2 个真实项目、合计至少 10 人连续使用 4 周，期间没有丢失数据，也没有需要手工修数据的事故。
2. **文件锁**：Locks API 验收通过；`git yunbox init` 不再设置 `lfs.locksverify=false`，未持有锁的人无法 push 被锁文件的修改。
3. **自助身份**：新成员用云乐坊账号登录网页，就能自己签发、查看和吊销 token；管理员只负责给仓库授权，不再手动转交 token。token 有过期时间。
4. **可观测**：5xx 比例、batch 延迟、COS 请求错误、费用超预算都有告警，并发到固定的通知渠道；每次 push、锁操作和 token 操作都有审计日志可查。
5. **可恢复**：完成一次恢复演练，覆盖误删对象、覆盖对象、token 数据或锁数据损坏、整个服务重新部署四种情况，并把恢复步骤写进运维手册。
6. **安全**：完成一次安全复查（越权、重放、凭据泄露、日志脱敏、最小权限、依赖漏洞），没有未处理的高危问题；运行时不使用长期密钥。
7. **性能**：单个 2 GB 文件可以上传和下载；一次 batch 1000 个对象在 5 秒内返回；10 人同时 push 时没有失败。指标在阶段 6 压测时确认。
8. **分发与跨平台**：CLI 发布到 npm；Windows（PowerShell 和 Git Bash）、macOS、Linux 上完整走通 init、push、clone、加锁和解锁。
9. **文档**：接入指南、从 GitHub LFS 迁移的指南、运维手册（部署、升级、告警处理、恢复）齐全，一个没参与开发的人照着能完成。

## 已定决策

2026-10-17 确认采用下表的推荐默认值：

| 决策 | 结论 | 理由 |
|---|---|---|
| 生产范围 | 云乐坊内部项目，合计不超过 30 人 | 规模决定了不需要分片上传、多地域和复杂的配额系统 |
| 元数据存储（token、锁、审计日志） | 改用 CloudBase 文档数据库，对象和已校验标记继续放在 COS | COS 的普通 PUT 不支持按 ETag 条件写入，锁需要原子的「不存在才创建」；数据库同时解决了 token 文档并发覆盖的问题（plan.md 第 12 节风险）。云托管里访问数据库的方式**未核实** |
| 文件锁 | 实现 Git LFS Locks API（创建、列出、verify、解锁、管理员强制解锁），锁不自动过期 | Git LFS 客户端的锁语义就是不过期，由持有人或管理员解锁；自动过期可能让两个人同时改同一个文件 |
| token 签发 | 保留个人 token 作为 git 凭据，新增云乐坊 SSO 登录的自助网页（复用 `@yunlefun/sso`）；token 默认 90 天过期 | git-lfs 只认 Basic 认证，不能直接用 SSO；网页只负责签发和吊销 |
| 仓库授权 | 管理员在网页上按用户授权仓库，替代手写 `repos` 映射 | 30 人规模下手写 JSON 容易出错 |
| 备份 | 开启 COS 版本控制，历史版本保留 30 天；数据库开启平台自动备份；不做跨地域复制 | 能覆盖误删、误覆盖；地域级故障按「可接受停机、数据不丢」处理，写进运维手册（COS 版本控制和数据库备份的具体能力**未核实**） |
| 告警渠道 | 企业微信群机器人 | 团队日常在用 |
| CLI 分发 | 发布 npm 包 `yunbox`；只有阶段 0 的试点证明有人没有 Node.js 时，才做单文件可执行程序 | npm 包名可用；单文件程序的成本较高 |
| 对象清理 | 不做自动删除；提供按仓库统计用量的管理命令 | 误删的风险远大于存储费用；清理要扫描所有仓库历史，仍按 plan.md 第 7 节暂缓 |
| 迁移已有 LFS 历史 | 只写迁移指南（`git lfs fetch --all` 后 `git lfs push --all`），不做专门的工具 | 一次性操作，指南加 `doctor` 检查足够 |

### 阶段 2：文件锁

- 实现 Git LFS Locks API：`POST /locks`、`GET /locks`、`POST /locks/verify`、`POST /locks/:id/unlock`（含 `force`）。创建锁必须是原子的，同一路径不能有两把锁；强制解锁只允许管理员。
- 读权限可以列出锁，写权限才能加锁和解锁自己的锁。
- `init` 改为启用锁校验，`.gitattributes` 支持按类型加 `lockable`；`doctor` 检查锁接口可用。
- 端到端测试用真实 git-lfs：两个用户争同一个文件的锁、未持锁 push 被拒、解锁后另一人可以加锁、强制解锁。

### 阶段 3：自助身份与授权

- 新增 `apps/web`：云乐坊 SSO 登录（按 `yunle-subapp-onboarding` 的约定），用户自助签发、查看、吊销自己的 token（明文只显示一次）。
- 管理员页面：按用户授权仓库读写、查看和强制解除锁、吊销任何人的 token。管理员身份由服务端配置指定。
- 服务端的管理接口和 LFS 接口分开鉴权：管理接口用 SSO 会话，LFS 接口继续用 token。
- G1 的「只读素材列表加图片预览」可以在这里顺带做，不作为完成标准。
